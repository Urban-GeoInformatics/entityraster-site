entityraster

Raster-valued attributes for GeoPandas. One raster per row, handled like any other column.

Keep a person's activity space, a site's suitability surface or a parcel's land-cover map in a table, next to the entity's other attributes. Filter, group, join and save it the way you already do with tables. We call such a table a GeoRasterFrame: an ordinary (Geo)DataFrame in which one column has the pandas dtype raster.

import entityraster as er

gdf = er.embed(people, "rasters/", on="uid", pattern="p{uid:05d}.tif",
               column="activity_space", index="uid")

gdf.loc[200, "activity_space"].mean()                                  # one person's raster
gdf["area_km2"] = gdf["activity_space"].raster.area(0.5, relative=True) / 1e6
old = gdf[gdf["age"] > 60]                                             # rasters follow the filter
old.rst.surface("activity_space", by="gender", outside="unknown")      # a mean surface per group

Why a raster column?

The usual way to work with one raster per person is a path column and a hand-written loop that opens each file, aligns arrays, accumulates results and merges them back. That is long, and it is where silent errors hide: rasters with different origins stacked as if they were aligned, cells outside a raster treated as zero or as missing without anyone deciding. entityraster keeps a reference to each raster, with its metadata, in the table, reads pixels only when needed, refuses to guess when rasters do not line up, and makes you state what cells outside a raster mean.

What it does

  • Attach rasters by key (embed): catalogue, file-name pattern or template, folder, path column. Unmatched rows, duplicate keys and unused files are reported, never silently dropped.
  • Lazy. The table holds references and metadata; pixels are read only for the rows an operation needs.
  • Per entity, every entity, across entities: gdf.loc[uid, col].mean(), gdf[col].raster.area() as a column, gdf.rst.surface(col, by="group", outside=...) as a map per group.
  • Rasters with different extents are aligned with strict, explained rules; reproject=, resampling= and snap= are opt-in, and errors name the rows and the fix.
  • Weighted analysis and land use: exposure weighted by each entity's raster, class shares per entity, and zonal_composition for one land-use map over many polygons.
  • Plain pandas: filter, groupby, merge, concat, sjoin, to_crs and dissolve keep working; save to GeoParquet with references; export surfaces as GeoTIFF for QGIS and ArcGIS.

Zero or unknown?

Every operation across entities requires outside="zero" or outside="unknown". Leaving it out is an error, because the choice changes the numbers.

Is it the right tool?

Your jobUse
One raster per entity, different extents, kept with the entity's attributesentityraster
One shared raster, many polygons (zonal statistics)rasterstats, exactextract, or er.zonal_composition
A stack of aligned rasters (time series, data cube)xarray / rioxarray
Very large collections in a SQL engineSedonaDB, Apache Sedona, PostGIS raster

Measured against a rasterio loop and idiomatic xarray on five tasks: 7 lines instead of 121 and 62, about the same speed as the loop, and the only one of the three that stops on misaligned rasters without hand-written checks. Details in How it compares.

pip install entityraster

Limitations

  • Evaluated on synthetic data; not yet benchmarked on large real collections.
  • North-up GeoTIFFs, one band per reference; single process, no parallelism.
  • The table stores file paths: moving the files breaks the references.
